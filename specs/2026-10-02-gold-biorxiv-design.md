- 상태: 승인(2026-10-02). 구현 계획을 쓰며 시제품으로 확인한 내용을 3, 4.1, 4.3, 4.4, 4.6, 4.7, 5, 9에 반영함
- 기반: `specs/2026-09-30-gold-dev-design.md` (정답 점수와 1단계 판정 규칙), `specs/2026-09-29-engine-design.md` (프로토콜 1.0.5)

## 1. 목적과 범위

**프레임워크가 작동하는지(1단계)를 실제 과학 결과로 확인해요.**
- 합성 세트(B)는 모든 구간에서 천장이었어요. 모델들이 맞춤을 직접 계산해 내서, 같은 과제 안에서 답이 갈리지 않았거든요(`specs/2026-10-01-gold-synth-design.md`).
- 이번 세트의 정답은 계산으로 구할 수 없어요. 실제 연구가 무엇을 보고했는지가 정답이기 때문이에요.

**과제 한 개:** 2026-07-01 이후 처음 게시된 bioRxiv 프리프린트 하나로 만들어요.
- 초록의 배경·방법 문장을 보여 줘요.
- 결과 후보 3개를 보여 줘요. 진짜 결과 1개와 바꾼 결과 2개예요.
- "이 연구가 실제로 보고한 결과는 무엇인가"를 순위로 묻는 BrainBench 방식(Luo et al., Nature Human Behaviour 2024)을 3지선다로 바꾼 것이에요.

**인터뷰에서 정한 것 (2026-10-02)**
- 출처: bioRxiv, 초록만 써요.
- 분야: 생의학 5개 분야에서 같은 수씩 뽑아요. 약리·독성학, 암생물학, 면역학, 신경과학, 세포생물학이에요.
- 바꾼 결과: 패널 밖의 다른 계열 모델인 DeepSeek-V4-Flash(로컬 cp088)가 써요. 결과만 보고도 진짜가 티 나는 항목은 자동으로 버려요. 사람은 표본만 검토해요.
- 순서: 파일럿 5과제(분야당 1개)를 먼저 돌리고, 천장도 우연 수준도 아니면 본 세트 20과제(분야당 4개)로 1단계를 판정해요.

**범위 밖**
- 본문 사용, 사람이 쓴 변조문, medRxiv 등 다른 서버
- 2·3단계 실행과 그 판정 기준
- 사람 전문가 기준선

## 2. 성공 기준

1. 같은 저장 입력(고정한 bioRxiv 목록, 저장한 DeepSeek 출력, 검토 기록)에서 같은 과제·정답 파일이 다시 만들어져요.
2. 모든 과제의 맥락은 초록의 배경·방법 문장만으로 되어 있어요. 진짜 결과는 초록의 결과 문장들 그대로예요.
3. 엔진은 정답 파일을 읽지 않아요. 새 모듈은 `reasonlineage.gold` 패키지 안에 있어요.
4. 수집 거르기, 표본 순서, 문장 나누기 검사, 변조 검사, 티 거르기 규칙, 파일 쓰기를 테스트로 확인해요. 테스트는 모델과 bioRxiv를 부르지 않아요.
5. 파일럿을 돌려 규칙대로 다음 단계를 정하고, 본 세트까지 가면 1단계 판정을 보고해요.

## 3. 구조

| 파일 | 하는 일 |
|---|---|
| `src/reasonlineage/gold/biorxiv.py` (새) | 목록 받기와 거르기, 표본 순서, 문장 나누기, DeepSeek 요청과 검사, 티 거르기, 과제·정답 파일 쓰기 |
| `scripts/build_biorxiv.py` (새) | `fetch` → `candidates SET` → (검토) → `build SET` |
| `~/.cache/reasonlineage/biorxiv/pool.json` | 받은 목록 전체(초록 포함, 약 9MB). 저장소에 넣기엔 커서 캐시에 둬요 |
| `gold/biorxiv/pool.json` | 목록의 색인(DOI, 분야, 날짜)과 전체 목록의 sha256. 세트들이 함께 써요 |
| `gold/<SET>/` | `candidates.json`(DeepSeek 출력 포함), `review_sheet.md`, `review.json`, `gold.json` |
| `tasks/<SET>/` | 과제 파일 |
| `src/reasonlineage/diagnose/gold.py`, `cli.py`, `scripts/run_gold.sh` | 1단계 분석 보고서(`analysis.md`): `reasonlineage gold --analysis` |

**그대로 다시 쓰는 것:** `build.shuffled`, `scripts/run_gold.sh SET`, `reasonlineage gold`, 정답 점수와 1단계 판정, 엔진의 `HttpBackend`(DeepSeek 호출), 합성 세트 때의 실행 스크립트 방식(분리 실행, 이어 돌리기 최대 3번). 엔진은 바꾸지 않아요.

**세트 이름:** 파일럿은 `biorxiv-pilot`, 본 세트는 `biorxiv-v1`이에요.

**흐름**

```
bioRxiv API ── fetch ──> gold/biorxiv/pool.json (2026-07-01 ~ 2026-10-01, 5개 분야)
   │ candidates SET (DeepSeek: 나누기 → 변조 → 티 거르기, 출력 저장)
   ▼
gold/SET/candidates.json + review_sheet.md ── 사람 검토 ──> review.json
   │ build SET (모델 호출 없음, 결정적)
   ▼
tasks/SET/*.json + gold/SET/gold.json ── run_gold.sh SET ──> report.json
```

## 4. 과제 만들기

### 4.1 목록 받기 (`fetch`)
- API: `https://api.biorxiv.org/details/biorxiv/2026-07-01/2026-10-01/<cursor>?category=<분야>`
  - 분야는 `pharmacology_and_toxicology`, `cancer_biology`, `immunology`, `neuroscience`, `cell_biology`예요.
  - 2026-10-02에 확인한 기간 안의 신규 논문 수는 각각 174, 683, 584, 2,678, 821편이에요.
- 남기는 기록(모두 만족)
  1. `version`이 `"1"`이고, `date`가 2026-07-01 이후예요. 첫 공개가 7월 이후라는 뜻이에요.
  2. `type`이 `"new results"`예요.
  3. `published`가 `"NA"`예요. 이미 학술지에 실린 논문은 언제 실렸는지와 상관없이 빼요.
  4. 초록이 120단어 이상이고, 제목이나 초록이 철회(withdrawn)를 알리지 않아요.
  5. 어느 버전에서든 철회되지 않았어요(`type`이 `withdrawn`이거나 제목이 WITHDRAWN인 버전이 있으면 빼요).
  6. 초록의 API 표기를 실제 글자로 바꿀 수 있어요. `{beta}`→β, `{micro}`→µ, `{degrees}`→°, `{+/-}`→±, `[&ge;]`→≥, `&lt;`→< 등이에요. 진짜 결과는 원문이라서, 표기가 남으면 바꾼 결과와 표기만으로 구별돼요. 목록·그림 흔적(`O_LI`, `C_LI`, `O_FIG`), 본문에 붙은 소제목(`BackgroundThe…`), 모르는 표기가 남는 초록은 빼요.
- 남긴 기록의 DOI, 제목, 분야, 날짜, 초록을 DOI 순서로 캐시의 `pool.json`에 저장해요. 저장소의 색인에는 DOI·분야·날짜와 전체 목록의 sha256을 적어요. 받은 원본 페이지도 캐시에 둬요.
- 서버가 가끔 연결을 끊어서, 페이지마다 쉬었다가 최대 4번까지 다시 받아요(2026-10-02 시제품에서 한 번 일어남).
- 2026-10-02에 받은 목록은 4,792편(약리·독성 167, 암 666, 면역 570, 신경 2,593, 세포 796), 초록 중앙값 211단어예요.

### 4.2 표본 순서
- 분야마다 DOI 순서로 정렬한 뒤, `<SET>:<분야>`를 열쇠로 한 고정 seed로 섞어요(`build.shuffled`).
- 앞에서부터 하나씩 꺼내서, 4.3–4.5를 모두 통과한 논문을 분야 할당량만큼 남겨요. 할당량은 파일럿 1, 본 세트 4예요.
- 본 세트는 파일럿 논문(파일럿 `candidates.json`의 DOI)을 건너뛰어요.

### 4.3 문장 나누기 (DeepSeek)
- 코드가 초록을 문장으로 나누고 번호를 붙여요. 약어(e.g., et al., Fig.), 이니셜(J., K. pneumoniae), 소수점에서는 나누지 않아요. 숫자 뒤("2D.")나 소문자·그리스 문자로 시작하는 문장("scRNA-seq…", "β-cells…")에서는 나눠요.
- DeepSeek는 이 연구 자체의 발견이나 결론을 말하는 첫 문장의 번호만 답해요(JSON `{"first_result": n}`). 새 문장은 쓰지 않아요.
- 맥락은 그 앞의 문장들, 진짜 결과는 그 문장부터 끝까지예요. 원문 문장만 쓰니까 원문 일치는 저절로 보장되고, 결과는 늘 초록 끝의 한 덩어리예요.
- 버리는 경우
  - 맥락 문장이 하나도 없는 경우
  - 결과 문장이 하나도 없는 경우
  - 결과가 400단어를 넘는 경우
- 제목은 보여 주지 않아요. 제목이 결과를 말하는 경우가 많아서예요.

### 4.4 바꾼 결과 2개 (DeepSeek)
- 입력은 맥락과 진짜 결과예요. 출력은 JSON `{"reversed": …, "altered": …}`예요.
  - `reversed`: 핵심 결과 하나의 효과 방향을 뒤집어요(증가↔감소, 촉진↔억제, 있음↔없음). 방법의 성능을 보고하는 초록이면 방법이 실패했다고 쓰지 않고, 어느 비교·조건·집단에서 효과가 났는지를 뒤집어요.
  - `altered`: 방향은 두고 크기·조건·대상·기전 중 하나를 그럴듯하게 바꿔요.
  - 둘 다 배경·방법에 적힌 어떤 사실(생물, 세포, 표적, 기법, 정의, 수치)과도 모순되면 안 돼요. 연구가 '찾아낸 것'만 바꿔요. 첫 파일럿에서 패널이 이런 모순을 근거로 변조문을 지웠어요(5.1).
  - 둘 다 저자가 실제로 낼 법한 결과처럼 읽혀야 해요. 저자의 자신 있고 긍정적인 논조를 지키고, 불가능한 값(음수 비율 등)을 쓰지 않고, 원문과 문장 수·길이·문체·숫자 형식을 맞춰요. 원문과도 서로와도 분명히 다른 결론이어야 해요.
  - 2026-10-02 시제품에서 처음 지시로는 `reversed`가 "억제율 −39%", "이 방법은 쓸모없다" 같은 실패한 연구 문장이 되어 내용을 몰라도 지울 수 있었어요. 위 지시로 고치자 논조를 지키는 미묘한 변조가 나왔어요.
- 코드가 확인해요. 아래 중 하나라도 걸리면 버려요.
  - 두 변조문이 원문이나 서로와 같아요(공백 무시).
  - 길이가 원문의 0.75–1.25배를 벗어나요.
  - JSON이 아니에요.

### 4.5 티 나는 항목 거르기 (DeepSeek, 새 대화)
- 맥락 없이 결과 3개만 보여 주고 "어느 것이 실제 발표된 원문인가"를 물어요. 순서를 세 가지로 돌려 3번 물어요.
- 3번 모두 진짜를 고르면 문체로 티가 나는 것이니 버려요. 우연히 3번 다 맞힐 확률은 1/27이에요.
- **맥락 거르기** (첫 파일럿 뒤 추가): 같은 방식으로 이번에는 배경·방법까지 보여 주고 3번 물어요. 3번 모두 진짜를 고르면, 결과를 예측하지 않고 맥락과의 일치만으로 풀리는 것이니 버려요.

### 4.6 사람 검토 (`review.json`)
- 검토표(`review_sheet.md`)는 과제마다 맥락, 진짜 결과, 바꾼 결과 2개를 표시해서 보여 줘요.
- 검토자는 사용자예요. 검토 표본은 분야마다 표본 순서상 처음으로 남은 논문이에요. 파일럿은 그래서 5과제 모두이고, 본 세트는 20개 중 5개예요.
- 기준: 두 변조문이 그럴듯하면서도 진짜와 확실히 다른 결론인지, 맥락에 결과가 새지 않았는지예요.
- 형식: `{"keep": [doi, …], "drop": [{"doi": …, "why": …}]}`예요.
- 버린 항목은 그 분야의 다음 논문으로 바꾸고, 그 논문도 검토해요. 버린 논문은 `candidates.json`에 남아서 검토 기록이 계속 그 논문을 가리킬 수 있고, 분야 할당량에는 세지 않아요. 검토하지 않은 표본 과제가 있으면 `build`가 멈춰요.

### 4.7 과제·정답 파일 (`build`)
- 과제 id는 `<SET>-01`, `-02`, …이고, 분야 순서 → 표본 순서로 매겨요.
- 후보 이름은 `Result A`, `Result B`, `Result C`예요. 진짜 결과의 글자는 세트 안에서 A·B·C에 고르게 나누고(차이 최대 1), 그 순서는 세트 이름을 열쇠로 섞어요. 나머지 두 글자는 과제 id를 열쇠로 섞어요. 과제마다 따로 섞으면 파일럿 5과제 중 4개의 정답이 A가 되어, 첫 보기를 고르는 경향이 정답률을 부풀릴 수 있었어요(최종 검토).
- 질문(영어):

```
<맥락>

Three candidate results follow. Exactly one is what this study reported.
- Result A: <…>
- Result B: <…>
- Result C: <…>
Which result did this study report? Rank the candidates, and give the mechanism, the key evidence, and a validation experiment for the top pick.
```

- 과제 파일은 엔진 과제 형식이에요(`category: analytical`, `data_sensitivity: public`).
- `gold.json`은 개발용 세트와 같은 형식이에요. 진짜 결과의 글자가 `approved`, 나머지 둘이 `failed`이고, 과제마다 `doi`도 적어요. `source`에는 API, 기간, 목록의 sha256, DeepSeek 모델, 분야당 과제 수를 적어요.
- DeepSeek 출력은 같은 seed로도 달라져요(2026-09-29 확인). 그래서 `candidates`가 저장한 출력으로만 `build`해요. 다시 만들 때도 DeepSeek를 부르지 않아요.
- 과제 폴더에 이번 `build`가 만들지 않는 파일이 있으면 멈춰요.

## 5. 실행 계획 (실행 전에 고정)

### 5.1 파일럿 (`biorxiv-pilot`, 5과제)
- 검토를 마친 뒤 `scripts/run_gold.sh biorxiv-pilot`로 돌려요.
  - 조건: 0세대만, 프로토콜 1.0.5, seed 1, 실험 모드, 이해관계자 배제, 맥락 격리, 웹 검색 없음, 패널 opus·gpt-6.1-sol·grok-4.7·glm-5.3.
  - 분리 실행이고, 멈춘 실행은 5분 뒤 이어 돌려요(최대 3번).
- **규칙:** 답 20개 중 정답을 1위에 둔 비율(`share_correct`)로 정해요.
  - 0.8 이상: 천장이에요. 멈추고 설계를 고쳐요(예: 더 미묘한 변조).
  - 0.375 이하: 우연 수준(1/3)이에요. 멈추고 과제를 점검해요.
  - 그 사이: 본 세트로 가요.
- 파일럿은 판정에 넣지 않아요.
- **첫 파일럿 결과 (2026-10-02, `biorxiv-pilot`):** 답 20개 중 19개 정답(0.95), 쌍 3개로 천장이었어요. 모델들은 바꾼 결과가 배경과 모순되는 점을 근거로 지웠어요. 예를 들어 배경은 "중뇌 모노아민 중추"인데 바꾼 결과는 "GABA성"이었어요. 사용자와 정해서 바꾸기 지시에 모순 금지를 넣고 맥락 거르기를 더했어요(4.4, 4.5).
- **두 번째 파일럿 (`biorxiv-pilot2`):** 첫 파일럿 논문을 뺀 새 표본으로, 같은 검토와 규칙을 따라요.
- 실행 스크립트는 판정 요약(`report.json`)과 함께 분석 보고서(`analysis.md`)를 써요. 보고서에는 판정, 저자별 정답률, 심사위원별 일치도, 저자×심사위원 평균 점수표, 과제마다 각 답의 1위 후보·정답 여부·적합도가 들어가요.

### 5.2 본 세트 (`biorxiv-v1`, 20과제)
- 두 파일럿의 논문을 뺀 새 표본으로 만들고(`--exclude-set biorxiv-pilot --exclude-set biorxiv-pilot2`), 표본 5과제를 검토한 뒤 같은 조건으로 돌려요.
- 결과를 본 뒤 과제나 판정 기준을 바꾸지 않아요.

### 5.3 비용
- 과제당 모델 호출은 16회(답 4 + 심사 12)이고, J1 점검(jev)이 4회예요. 글 이해 과제라 과제당 15–30분으로 봐요.
- 파일럿은 1.5–2.5시간, 본 세트는 5–10시간이에요.
- DeepSeek 호출은 논문당 8회 안팎(나누기 1, 변조 1, 티 거르기 3, 맥락 거르기 3)이고, 로컬이라 비용이 없어요.
- 모델을 부르는 실행은 각각 사용자에게 먼저 물어요.

## 6. 채점과 판정
- 정답 점수와 1단계 판정은 개발용 설계 6.1–6.2를 그대로 써요. 진짜 결과가 1위면 1점, 2위면 0.5점, 3위면 0점이에요.

| 조건 | 판정 |
|---|---|
| 완전히 맞힌 비율 ≥ 80% | 보류(천장) |
| 정답이 갈리는 답의 쌍 < 10 | 보류 |
| 적합도-정답 일치도 ≥ 0.70 | 신호 |
| 그 밖 | 신호 없음 |

- 동점은 0.5로 세요.
- 결과를 본 뒤 기준을 바꾸지 않아요.

## 7. 오류 처리
- **bioRxiv API 실패:** 무엇이 실패했는지 알리고 멈춰요. 받은 페이지는 캐시에서 다시 써요.
- **DeepSeek 실패나 형식 오류:** 한 번 다시 묻고, 그래도 안 되면 그 논문을 건너뛰어요. 건너뛴 이유는 `candidates.json`에 적어요.
- **분야의 논문이 바닥남:** 몇 개까지 찼는지 알리고 멈춰요.
- **거부가 논문 때문인지 먼저 확인해요.** 2026-10-02에 Opus가 짧은 시간 안에 거의 모든 과제를 거부하는 일이 있었어요. 이미 정상으로 측정한 과제까지 거부됐으니 논문 탓이 아니었어요. 그래서 논문을 빼기 전에 **이미 정상으로 돌아간 과제를 같은 프롬프트로 다시 물어봐요.** 그것도 거부되면 제공자 상태 문제이니, 논문은 그대로 두고 기다렸다가 다시 돌려요.
- **한 분야가 모자랄 때:** `build --limit FIELD=N`으로 그 분야만 과제를 줄여요. 정답 글자는 선언한 크기(분야당 과제 수 × 5분야)로 뽑아서, 한 분야가 줄어도 이미 측정한 과제의 글자가 바뀌지 않아요.
- **제공자 안전 분류기에 걸린 논문:** 어떤 패널 멤버의 제공자가 그 초록을 안전 사유로 거부하면, 다시 묻거나 문구를 바꾸지 않고 그 논문을 `review.json`의 `drop`에 사유와 함께 적고 같은 분야의 다음 논문으로 바꿔요. 1단계는 같은 심사위원 4명이 모두 보아야 하므로 한 명이 못 보는 과제는 쓸 수 없어요. 2026-10-02 본 세트에서 한 편이 이렇게 빠졌어요(codex의 gpt만 거부, 다른 세 멤버는 정상 심사).
- **검토 기록 오류:** 검토하지 않은 표본 과제, 모르는 DOI, 중복, 이유 없는 버림이 있으면 `build`가 멈춰요.
- **이전 파일이 남음:** 과제 폴더에 이번 `build`가 만들지 않는 파일이 있으면 멈춰요.

## 8. 테스트
모델과 bioRxiv는 부르지 않아요. 가짜 응답을 써요.
- **목록 거르기:** 버전, 날짜 경계(7월 1일 포함), 유형, `published`, 초록 길이, 철회를 확인해요. 페이지 넘기기도 확인해요.
- **표본 순서:** 같은 세트면 같은 순서, 다른 세트면 다른 순서인지 확인하고, 본 세트가 파일럿 DOI를 건너뛰는지 확인해요.
- **문장 나누기:** 약어와 소수점을 확인하고, 4.3의 버리는 경우를 확인해요.
- **변조 검사:** 같은 문장, 길이 범위, JSON 오류를 확인해요.
- **티 거르기:** 3번 모두 맞힌 경우만 버리는지 확인해요.
- **파일:** 엔진이 과제를 읽는지(`load_task`), 정답 파일이 채점 코드의 후보 집합 검사를 통과하는지, 글자 섞기가 결정적인지, 질문에 제목과 결과 문장이 새지 않는지, 이전 파일이 있으면 멈추는지 확인해요.
- **검토 기록 검사:** 4.6의 오류들을 확인해요.
- **스크립트:** `build_biorxiv.py` 세 단계의 인자와 오류 안내를 확인해요.
