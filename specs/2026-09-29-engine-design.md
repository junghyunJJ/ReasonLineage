# ReasonLineage 엔진 설계 (1단계)

- 날짜: 2026-09-29
- 상태: 설계 1/3 · 2/3 · 3/3 승인, 문서 검토 대기
- 전체 설계 그림: https://claude.ai/artifact/3p69misGoKK1LzhovL3Rct
- 이전 스킬: `archive/reasonlineage-skill-v1.6.0/` (태그 `skill-v1.6.0`)

## 1. 목적과 범위

패널의 여러 모델이 답을 쓰고 서로 채점하면서 세대를 거쳐 답을 다듬는 엔진이에요. 누가 쓰고, 누가 채점하고, 무엇이 점검하는지를 코드로 고정해서 **심사 편향 논문**의 실험을 조건마다 같은 절차로 돌려요. 같은 엔진을 실제 사용(탐색 모드)에도 써요.

심사 편향 논문의 질문: 모델이 자기 답을 채점하거나 심사 기록을 공유하면 세대가 갈수록 점수(fitness)만 오르고 실제 정답률은 제자리인가? 작성자를 채점에서 빼고 격리해서 채점하면 이를 막을 수 있나?

**이 문서의 범위 (1단계 엔진)**
- `run`, `resume`, `diagnose` 명령
- 패널 호출: CLI 3종(claude, codex, grok)과 OpenAI 호환 HTTP (Ollama cloud의 GLM)
- 점검기: J1 관문, J2 진단, jev와 DeepSeek 연결
- PMID 확인
- 기록, 이어 돌리기, 프로토콜 버전, 실험·탐색 모드, seed와 replay
- 테스트

**범위 밖 (각각 별도 문서로 다뤄요)**
- 약물 재창출 정답지 v0 구축과 정답지 채점
- E1 비교 실험 (점검기 검증)
- 논문 분석 스크립트 (관대함·자기선호 추정, 조상 선호 분석)
- SKILL.md 대화형 앞단, LangGraph 버전
- 웹 검색 옵션, 2단계(LLM 상황 판단)와 3단계(스스로 진화하는 프로토콜)

## 2. 성공 기준

1. 실험 모드에서 같은 과제와 같은 0세대로 여러 조건을 돌리면, 조건 축 말고는 절차가 모두 같아요 (테스트로 확인).
2. 아무 지점에서 끊겨도 `resume`으로 끝까지 가고, 끊지 않은 실행과 엔진의 결정이 같아요.
3. `--replay`로 이전 실행의 결과를 그대로 재현해요.
4. 점검기 결과는 선택으로 새지 않아요. J1의 다시 쓰기 결정 하나만 예외예요.
5. 가짜 패널로 3세대 실행 테스트를 통과하고, 실제 패널로 파일럿 1회를 끝까지 돌려요.

## 3. 구조 (설계 1/3)

### 3.1 방식
단계별로 도는 평범한 Python 비동기 엔진이에요. 모든 호출 결과를 기록에 남기고, 기록에서 이어 돌 수 있어요. LangGraph는 나중에 붙여요.

### 3.2 코드와 LLM의 역할

| 코드(엔진)가 하는 일 | LLM이 하는 일 |
|---|---|
| 누가 채점하나, 심사위원이 무엇을 보나 | 답 쓰기 (첫 답, 변이, 교차) |
| 점수 계산 (차원별 중앙값, 가중 합) | 채점과 비판 |
| 선택, 세대 세기 | 교차에서 부모의 어떤 부분을 버릴지 |
| 기록, 프로토콜 버전, 모드 검사 | |

### 3.3 정책과 단계
판단 지점은 모두 바꿔 끼울 수 있는 **정책**으로 만들어요. 1단계는 모든 정책이 고정 규칙이에요.

| 판단 지점 | 1단계 고정 규칙 |
|---|---|
| 무엇을 변이하나 | 1위 생존자 |
| 누가 변이하나 | 그 답의 작성자 |
| 교차 부모 | 생존자 전원 |
| 누가 교차하나 | 부모를 쓰지 않은 모델 중 생존자가 가장 적은 모델. 같으면 최근에 교차를 맡지 않은 모델, 그래도 같으면 명단 순서 |
| 이상 출력 처리 | 5.10의 규칙 |
| 언제 멈추나 | 실험 모드는 세대 수 고정, 탐색 모드는 6.6의 규칙 |

- 1단계: 정책 인터페이스, 이상 출력 처리, 프로토콜 버전, 모드 전환, 실험 조건 두 축
- 2단계: LLM 상황 판단 정책 (탐색 모드 전용)
- 3단계: 스스로 진화하는 프로토콜 (정답지와 파일럿이 나온 뒤)

### 3.4 모듈 구성

```
src/reasonlineage/
  core/        지금 있는 것: categories, fitness, models, roles, selection, state
  backends/    지금 있는 것: claude_cli, codex_cli, grok_cli, roster
               새로: http.py (OpenAI 호환: Ollama cloud, vLLM)
  engine/      새로: runner(단계 진행), events(기록), replay(기록 재사용),
               header(실행 정보·프로토콜 해시), policies, conditions, config
  checks/      새로: 점검기 인터페이스, jev 클라이언트, 로컬 LLM 점검기,
               질문 세트, gate(관문 함수)
  diagnose/    새로: J2 실행, PMID 확인
  protocol/    새로: protocol.json과 프롬프트 파일 (해시 대상)
  cli.py       새로: run, resume, diagnose
```

`core`와 `engine`은 `checks`를 불러오지 않아요. `cli.py`가 `checks`로 관문 함수를 만들어 `engine/runner`에 넘기고, 엔진은 그 함수가 돌려주는 다시 쓰기 결정만 받아요 (9장 테스트 4).

## 4. 참여자

### 4.1 패널: 답을 쓰고 서로 채점해요

| 이름 | 모델 | 회사 | 부르는 방법 | 추론 설정 |
|---|---|---|---|---|
| opus | `claude-opus-5-5` | Anthropic | claude CLI | xhigh |
| gpt | `gpt-6.1-sol` | OpenAI | codex CLI (0.159.2) | xhigh |
| grok | `grok-4.7` | xAI | grok CLI | xhigh |
| glm | `glm-5.3` | Z.ai | Ollama cloud HTTP, `https://ollama.com/v1` | xhigh |

- 네 모델의 회사가 모두 달라서, 같은 계열끼리 봐주는 효과가 섞이지 않아요.
- 2026-09-30에 qwen(로컬 vLLM)을 glm으로 바꿨어요. 로컬 GPU 서버를 정리하기 위해서예요. deepseek 점검기는 로컬 vLLM에 그대로 둬요 (로그확률이 필요해요, 4.2).
- HTTP 호출은 `reasoning_effort`를 항상 명시하고 기록해요.
- Ollama cloud는 `response_format`을 무시해요. 그래서 HTTP 백엔드가 스키마를 시스템 메시지 끝에도 붙이고, 답의 마지막 JSON 객체를 출력으로 읽어요. 붙이기 전에는 GLM이 산문 뒤에 JSON을 붙여서 형식 B가 6번 중 1번만 맞았어요 (2026-09-30).
- Ollama 키는 `api_key_file`(`~/.config/reasonlineage/ollama.env`)을 프로그램이 직접 읽어요. Ollama cloud는 로그확률도 주지 않아요.
- 같은 계열 조건(5.8)에서만 쓰는 추가 모델: Sonnet 5.5(`claude-sonnet-5-5`), GPT-6 luna(`gpt-6-luna`).

### 4.2 점검기: 판정만 해요 (패널 밖)

| 이름 | 무엇 | 맡는 곳 |
|---|---|---|
| jev | TypeSafe System One, 버전 `jev-1.13.0` 고정 | 공개 데이터 과제(약물 재창출)의 J1·J2 |
| deepseek | `deepseek-ai/DeepSeek-V4-Flash-0731`, `reasoning_effort: "max"`, vLLM HTTP `http://esplhpc-cp088:6018/v1` | 비공개 데이터 과제의 J1·J2, E1 비교 |

- 과제 파일의 `data_sensitivity`로 점검기를 골라요. `public`이면 jev, `private`이면 deepseek예요.
- `private` 과제에서는 jev를 절대 부르지 않아요. jev 클라이언트가 스스로 거부하고, 테스트로 확인해요.
- CCI 과제도 공개 데이터셋을 써서 `public`이에요 (2026-09-30 결정). 그래서 지금은 모든 과제를 jev가 점검하고, deepseek는 E1 비교에 써요.
- E1에서 deepseek가 jev와 같은 지표로 5%p 이내면 공개 과제도 deepseek로 바꿔요. 지표는 E1 설계에서 정하고, 바꿀 때는 구성 파일의 `checker_for`를 고쳐요.
- 점검기는 답을 쓰지 않고, 채점하거나 고르지도 않아요. 패널 밖 모델을 쓰는 이유는 두 가지예요. 관문 판정이 다시 쓰기로 이어지니 패널 모델의 취향이 섞이면 안 되고, J2는 측정 도구라 측정 대상과 달라야 해요.
- jev는 공개 텍스트만 받아요. API 키는 환경 변수나 파일에서 읽고 저장소에 두지 않아요. 응답의 버전이 고정 버전과 다르면 실행을 멈춰요.
- deepseek는 jev처럼 확률을 내도록, 질문마다 한 번씩 부르고 마지막 답 토큰의 `top_logprobs`에서 선택지 확률을 읽어요. 로그확률 목록에는 추론 토큰도 들어 있으니 **마지막** 선택지 토큰을 읽어요. max로 추론하면 확률이 거의 0 아니면 1로 나와요.

### 4.3 격리
모든 호출은 새 세션으로 따로 부르고, 도구와 웹 검색이 없어요. 필요한 내용만 프롬프트로 받아요.
- claude: `--safe-mode --tools "" --no-session-persistence --system-prompt`, 프롬프트는 stdin으로 보내요 (구현 완료).
- codex: 사용자 설정과 규칙 무시, 기능 16개 끔, 웹 검색 끔, 읽기 전용, 빈 작업 폴더. 도구 사용 항목이 나오면 거부해요 (구현 완료).
- grok: 깨끗한 HOME, 빈 도구 목록. streaming-json에서 도구 호출이 보이면 거부해요 (구현 완료).
- http: 요청에 `tools`를 넣지 않고 system과 user 메시지만 보내요.
- 웹 검색은 실험 모드에서 쓰지 않아요. 정답지인 최근 임상 결과를 찾아 버리고, 회사마다 검색 엔진이 달라 비교가 흐려지고, 결과가 날마다 바뀌기 때문이에요.

## 5. 한 번의 실행 (설계 2/3)

### 5.1 과제 파일 (JSON)

```json
{
  "id": "ipf-001",
  "question": "Which approved drug is most promising to repurpose for idiopathic pulmonary fibrosis?",
  "candidates": ["metformin", "imatinib", "sildenafil"],
  "category": "biomedical",
  "data_sensitivity": "public"
}
```
- `candidates`가 있으면 순위는 이 항목을 빠짐없이 한 번씩 담아야 해요. 없으면(열린 질문) 모델이 항목을 직접 만들어요.
- `category`로 채점 차원과 가중치를 정해요 (5.6).

### 5.2 크기 규칙
모델 수 N에서 모델마다 첫 답 s = ⌈4/N⌉개, 개체 수 P = N·s, 생존자 k = P − 2예요. 세대마다 변이 1개와 교차 1개를 새로 만들어요.

| N | 첫 답 s | 개체 P | 생존자 k |
|---|---|---|---|
| 1 | 4 | 4 | 2 |
| 2 | 2 | 4 | 2 |
| 3 | 2 | 6 | 4 |
| 4 (파일럿) | 1 | 4 | 2 |

- s가 2 이상이면 첫 답마다 다른 접근을 지정해요. 순서는 기전 중심, 임상 근거 중심, 유전·오믹스 근거 중심, 안전성과 실현 가능성 중심이에요.
- N이 1이면 작성자가 새 세션에서 자기 답을 채점하고, N이 2이면 심사위원이 1명이에요. 두 경우 모두 신뢰도 경고를 기록해요.
- 파일럿은 0세대 뒤로 3세대를 돌려요. 선택은 0·1·2세대 뒤에 한 번씩, 모두 세 번 하고, 3세대가 끝나면 가장 높은 답을 결과로 저장해요.

### 5.3 흐름
1. **준비:** 과제 파일, 구성 파일, 프로토콜을 읽고 크기를 정해요. 실행 폴더와 실행 정보를 만들어요.
2. **첫 답 (0세대):** 모델마다 첫 답을 써요. 모든 답은 J1 관문을 거쳐요 (5.9).
3. **채점:** 조건에 맞는 심사위원이 따로따로 채점해요 (5.8). 차원별 중앙값을 가중 합해 fitness를 내요.
4. **선택:** 생존자 k개를 남겨요 (5.7).
5. **다음 세대:** 변이 1개와 교차 1개를 만들어 J1 → 채점 → 선택을 반복해요. 살아남은 답은 점수를 그대로 가지고 가고, 다시 채점하지 않아요.
6. **끝:** 가장 높은 답을 `result.json`에 저장해요. 실행 후 작업은 `diagnose`로 따로 해요 (7장).

### 5.4 역할별 규칙과 프롬프트
프롬프트는 SKILL.md v1.6.0의 역할 설명을 옮겨 `protocol/` 파일로 둬요.

| 역할 | 누가 | 받는 것 | 지시 |
|---|---|---|---|
| 첫 답 | 패널 모델마다 | 질문, 후보, (s ≥ 2이면) 접근 | 대담하게 쓰고, 망설이며 둘러대지 않기 |
| 변이 | 1위 생존자의 작성자 | 자기 답, 그 답의 심사위원 비판 | 비판을 하나씩 반영하되 잘된 부분은 보존하기 |
| 교차 | 부모를 쓰지 않은 모델 (3.3) | 생존자 전원과 각 부모의 비판 | 분해 → 가지치기 → 합성. 비판에 나온 약점은 가져오지 않기 |
| 채점 | 조건에 맞는 심사위원 | 질문, 답 산문, 최종 순위 블록 (조건에 따라 더 봄) | 엄격한 평가자. 차원별 0~1 점수와 비판 1~3개 |

- 변이는 작성자가 다른 모델의 비판을 받아 고치는 구조예요. 혼자 평가하고 혼자 고칠 때 생기는 자기 편향을 외부 비판으로 줄여요. 작성자가 분명해서 채점에서 뺄 모델도 분명해요.
- 교차로 나온 답은 합친 모델만 채점에서 빠지고, 부모 답을 쓴 모델은 채점에 들어가요. 부모 작성자까지 빼면 심사위원이 1명만 남기 때문이에요. 이 칸은 분석에서 따로 표시할 수 있게 기록에 부모와 작성자를 모두 남겨요.

### 5.5 답 형식 B

```json
{
  "answer": "자유롭게 쓴 설명",
  "ranking": [
    {"item": "metformin", "promisingness": 0.72, "confidence": 0.6, "pmids": ["29967351"]}
  ]
}
```
- `answer`: 모델마다 말투를 그대로 둬요. 자기 글을 알아보는 것이 자기선호의 원인이라서예요. 길이는 모든 모델에 같은 권장 범위(400~800단어, `protocol.json`)만 알려 주고 강제하지 않아요.
- `ranking`: 항목, 유망도(0~1), 확신도(0~1), `pmids`예요. CLI는 `--json-schema`(또는 같은 기능)로, HTTP는 `response_format`의 `json_schema`(strict)로 강제해요.
- `pmids`: 근거 논문 번호를 기억으로 적고, 모르면 빈 목록으로 둬요. 새로 쓰는 모든 답(첫 답, 변이, 교차, J1 다시 쓰기)에서 다시 적어요. 엔진은 번호를 채우거나 고치지 않아요.
- 심사위원은 산문 아래에 붙은 "최종 순위" 블록을 봐요. 이 블록에는 항목, 유망도, 확신도, PMID가 들어가요. 심사위원도 도구가 없어서 PMID가 진짜인지는 확인하지 못해요.

### 5.6 점수
- 심사위원은 차원마다 0~1 점수와 비판 1~3개를 내요 (`score_schema`).
- fitness = Σ_d w_d · median_j(s_jd) / Σ_d w_d. 심사위원들의 차원별 중앙값을 가중 합한 값이에요.
- **보정은 쓰지 않아요.** 2026-09-27 측정 데이터로 표본 밖 검증을 해 보니, 보정해도 이기는 답이 더 잘 맞지 않았어요 (원점수 21/24, 평균 보정 19/24, z-점수 20/24). 관대함과 자기선호는 논문 분석에서 따로 추정해요.
- 생의학(`biomedical`) 과제의 가중치:

| 차원 | 가중치 |
|---|---|
| evidenceCoverage (근거) | 0.30 |
| specificity (구체성) | 0.30 |
| novelty (새로움) | 0.20 |
| actionability (실행 가능성) | 0.20 |

### 5.7 선택
- 상위 k개를 남겨요. 우세 판정과 동점 판정의 기준은 모두 0.03이에요. 동점이면 작성자가 다양해지는 쪽을 골라요 (`select_survivors`).
- 선택은 기록된 점수만으로 정해지는 결정적 계산이에요.

### 5.8 실험 조건 두 축

| 축 | 값 | 심사위원 / 보는 것 |
|---|---|---|
| 누가 채점하나 | `recuse` (기본) | 작성자를 뺀 패널 전원 |
| | `self` | 작성자 혼자 (새 세션) |
| | `same_family` | 작성자와 같은 회사의 다른 모델 |
| | `other_vendor` | 작성자와 다른 회사의 모델 |
| | `all` | 작성자를 포함한 패널 전원 |
| 심사위원이 무엇을 보나 | `isolated` (기본) | 질문, 작성자가 받은 항목 규칙(프로토콜 1.0.1부터), 답 산문, 최종 순위 블록 |
| | `author_label` | 위 내용과 작성 모델 이름 |
| | `shared_trace` | 위 내용과 이전 선택까지의 점수표, 현재 개체들의 순위 블록 |

- `same_family`는 모든 작성자에게 같은 회사의 다른 모델이 명단에 있어야 해요 (예: Opus와 Sonnet 5.5, GPT sol과 luna). 짝이 없는 작성자가 있으면 실험 모드는 시작하지 않아요.
- 기본 패널에서는 네 모델의 회사가 모두 달라서 `other_vendor`와 `recuse`가 같아져요.
- `shared_trace`에는 채점이 진행 중인 점수를 넣지 않아요. 그래야 병렬 채점 순서와 관계없이 결과가 같아요.

### 5.9 J1 관문
답이 나올 때마다 점검기에 질문 3개를 물어요. jev는 요청 1번에 세 질문을 함께 보내고, deepseek는 질문마다 1번씩 불러요. 질문의 영어 원문은 `protocol.json`에 둬요.

| # | 형식 | 질문 | 쓰임 |
|---|---|---|---|
| ① | Choice | 답 유형: (a) 질문에 대한 답 (b) 거절 (c) 과제·자기 자신·정책에 대한 문구나 가짜 표시 (d) 채점자에게 하는 말 | 관문은 (a)의 확률만 봐요 |
| ② | Noul | 1위 항목에 구체적인 논증(이유, 기전, 근거 연구)이 있나 | 관문 |
| ③ | Score 0~3 | 순위 항목 중 논증이 있는 항목이 얼마나 되나 | 기록만 해요 |

- **E1 전에는 기록만 해요** (`j1.enforce: false`). 이때도 판정 기준 0.5로 "다시 쓰기였을 것"인지를 계산해 함께 기록해요.
- E1로 검증되면 기준값을 정하고 관문을 켜요. 켜진 뒤에는 ①이나 ②가 기준 아래일 때 같은 작성자가 1회 다시 써요. 다시 쓴 답도 결함이면 기록만 하고 그대로 채점으로 보내요. 점검기가 개체를 없애지는 않아요.
- ③은 E1에서 믿을 만하다고 나오기 전까지 관문에 쓰지 않아요. Score는 어려운 판단에서 단계 순서가 자주 뒤집힌다는 보고가 있어요.
- ①은 여러 경우를 한 질문에 묶었어요. E1에서 정확도가 모자라면 이 질문만 나눠요.
- 원래 답과 다시 쓴 답을 모두 저장해요.

### 5.10 이상 출력과 오류 처리

| 상황 | 처리 |
|---|---|
| 호출 실패 (시간 초과, 연결 실패, 스키마 불일치, 구조화 출력 없음, 도구 사용) | 같은 모델로 1회 다시 불러요 (백엔드 재시도) |
| 순위가 과제의 후보를 빠짐없이 한 번씩 담지 않음 | 같은 작성자에게 1회 다시 요청해요. 그래도 안 되면 작성 실패로 처리해요 |
| 순위 항목 이름이 산문에 나오지 않음 (대소문자 무시) | 같은 작성자에게 1회 다시 맞추라고 요청해요. 그래도 안 맞으면 기록하고 그대로 진행해요 |
| 재시도로도 작성 실패 | 실험 모드: 실행을 멈추고 기록하고, 고친 뒤 `resume`해요. 탐색 모드: 다른 패널 모델로 대체하고 기록해요 |
| 심사위원 호출이 끝내 실패 | 실험 모드: 멈추고 기록해요. 탐색 모드: 남은 심사위원으로 계속하고 경고를 기록해요 |
| 점검기 호출 실패 | 통과로 보고 기록해요. 점검기 장애가 진화를 막지 않게 해요 |
| jev 버전이 고정 버전과 다름 | 실험 모드: 멈춰요. 탐색 모드: 경고를 기록하고 계속해요 |

호출 시간 제한은 작성·변이·교차 900초, 채점 900초, 점검 120초예요. HTTP의 `max_tokens`는 작성 128k, 채점 128k, 점검 8k예요. 프로토콜 1.0.2(2026-10-01)에서 채점 480초·32k, 작성 64k를 올렸어요. 합성 정답지의 데이터표를 GLM이 손으로 다시 계산하느라 채점 한 건이 32k를 넘겨 잘렸기 때문이에요. 상한에 닿지 않는 호출은 그대로예요. 프로토콜 1.0.3(같은 날)에서는 심사 시스템 프롬프트 끝에 "You have no tools. Do every calculation you need in your own reasoning before you answer." 한 줄을 더했어요. 이 줄이 없으면 Grok이 합성 과제를 심사할 때 데이터표 계산을 건너뛰었어요(추론 약 300토큰). 어떤 답에는 점수를 모두 0으로 채운 빈 JSON을 냈고요. 넣고 나니 같은 심사 4번이 모두 정상 점수였어요(추론 2만 2천~3만 3천 토큰).

## 6. 기록, 이어 돌리기, 버전, 재현 (설계 3/3)

### 6.1 실행 폴더

```
runs/<실행 ID>/
  header.json    실행 정보
  events.jsonl   사건 기록 (추가만 해요)
  checks.jsonl   점검기 판정만 따로
  calls/         호출마다 요청 전문과 원래 응답 (<호출 이름>.json)
  result.json    최종 최고 답과 요약
  diagnostics/   실행 후 작업의 결과
```
`runs/`는 git에 올리지 않아요. 비공개 데이터가 들어갈 수 있어서 로컬에만 둬요.

**header.json에 남기는 것**
- 프로토콜 버전과 해시, 모드, 조건 두 축, seed
- 과제 파일 사본과 해시
- 패널: 이름, 백엔드, 모델 ID, 회사, 추론 설정, CLI 버전, HTTP 주소
- 점검기: jev 버전, deepseek 모델과 설정, `j1.enforce`
- `--replay`, `--gen0-from`의 원본 실행
- 엔진 git 커밋, 시작 시각

### 6.2 사건 기록
`events.jsonl`에는 한 줄에 사건 하나를 적어요. 줄마다 시각과 종류가 들어가요.

| 종류 | 내용 |
|---|---|
| `run.started` | 실행 시작 |
| `call.completed` | 호출 이름, 백엔드, 모델, 추론 설정, seed, 캐시 키, 소요 시간, 토큰, 재사용 여부, `calls/` 파일 |
| `candidate.created` | ID, 작성자, 작업(첫 답·변이·교차·다시 쓰기), 부모, 세대, 답 전문 |
| `judge.scored` | 답 ID, 심사위원, 차원별 점수, 비판, 조건 |
| `candidate.scored` | 답 ID, 심사위원 목록, 차원별 중앙값, fitness |
| `selection` | 세대, 생존자, 탈락자, 동점 처리 |
| `anomaly` | 종류, 처리 결과 |
| `run.stopped` / `run.completed` | 멈춘 이유 / 끝난 이유와 최고 답 |

`checks.jsonl`에는 `check.j1`을 적어요. 답 ID, 점검기, 질문별 답, 다시 쓰기였을지 여부, 관문 켜짐 여부가 들어가요. 논문 분석에 필요한 심사위원, 작성자, 부모, 세대, 조건이 모든 칸에 남아요.

### 6.3 이어 돌리기 (`resume`)
- 호출이 하나 끝날 때마다 결과를 바로 한 줄로 적어요. 호출마다 정해진 이름이 있어요: `g<세대>/<역할>/<답 ID>/<모델>` (예: `g1/judge/c06/opus`).
- 다시 시작하면 기록을 처음부터 읽어 같은 상태 기계로 상태를 되살리고, **기록에 없는 호출만** 새로 해요. 이미 받은 답은 다시 부르지 않아요. 모델 답은 부를 때마다 달라서, 다시 부르면 다른 실행이 돼 버리기 때문이에요.
- 선택은 기록된 점수로 다시 계산해서 기록과 같은지 확인해요. 다르면 멈춰요.
- 마지막 줄이 반쯤 써져 있으면 버려요.
- 다시 시작할 때 프로토콜 해시가 다르면 멈춰요. 모델 ID가 바뀌었으면 실험 모드에서는 멈추고, 탐색 모드에서는 경고를 기록하고 계속해요. CLI 버전만 바뀌었으면 기록하고 계속해요.

### 6.4 프로토콜 버전
- 프로토콜은 `protocol/` 폴더의 프롬프트 파일과 `protocol.json`을 묶은 거예요. `protocol.json`에는 크기 규칙, 0.03 기준, 차원과 가중치, 파일럿 세대 수, J1·J2 질문과 기준값, `j1.enforce`, 시간 제한, `max_tokens`가 들어가요.
- 해시는 이 파일들의 내용으로 계산해요. 한 글자만 바뀌어도 해시가 달라져요. 내용을 바꾸면 버전 번호도 올려요.
- 논문 분석은 프로토콜 해시가 같은 실행끼리만 비교해요.

### 6.5 seed와 replay
확인한 사실:

| 모델 | seed를 주면 같은 답이 나오나 |
|---|---|
| GLM (Ollama cloud) | 아니요. 같은 seed로 두 번 불러도 답이 달랐어요 (2026-09-30) |
| DeepSeek (vLLM) | 아니요. seed와 온도 0을 줘도 3번 모두 달랐어요 |
| claude, codex, grok CLI | seed 옵션이 없어요 |
| jev | seed가 없어요 |

- **`--seed <정수>`**: 두 모드 모두 써요. 안 주면 엔진이 임의로 정해서 기록해요. 엔진 안의 무작위 선택은 이 seed로 고정해요. HTTP 호출에는 호출마다 seed를 따로 만들어 보내요. 값은 `sha256("<실행 seed>:<호출 이름>:<시도 번호>")`의 앞 8자리 16진수를 정수로 바꾼 거예요.
- **`--replay <실행 폴더>`**: 이전 실행에 저장된 답을 다시 써서 같은 결과를 재현해요. 모든 모델에서 같은 결과가 나오는 방법은 이것뿐이에요.
  - 캐시 키는 백엔드, 모델, 추론 설정, system 프롬프트, user 프롬프트, 스키마(점검기는 질문 세트)를 정규화한 JSON의 sha256이에요.
  - 같은 요청이 여러 번 나오면 순서대로 맞춰요.
  - 키가 같은 호출만 저장된 답을 쓰고, 달라진 호출은 새로 부른 뒤 `call.completed`에 새 호출로 표시해요.
- **`--gen0-from <실행 폴더>`**: 실험 조건끼리 0세대를 공유할 때 써요. 원본 실행의 0세대 작성, J1 판정, J1 다시 쓰기를 재사용하고 채점부터 새로 해요. `--replay`와 같은 방식을 0세대에만 쓰는 거예요.
- `--replay`는 원본 실행의 seed와 조건을 그대로 이어받아요. 새로 부르는 호출에도 같은 seed 규칙을 써요. `--replay`와 `--gen0-from`은 함께 쓸 수 없어요.
- `resume`은 같은 실행 폴더를 이어 가는 거고, `--replay`는 다른 실행의 기록으로 새 실행을 만드는 거예요.

### 6.6 실험 모드와 탐색 모드

| | 실험 모드 (논문) | 탐색 모드 (실제 사용) |
|---|---|---|
| 세대 수 | 고정 (`--generations`, 기본값은 `protocol.json`의 3) | 최대 세대 수 안에서, 범주 기준(biomedical 0.75)에 닿으면 조기 종료. 2세대 동안 0.03 넘게 오르지 않으면 한 번 복구를 시도하고, 그래도 안 오르면 종료 |
| 0세대 첫 답 | 조건끼리 공유 (`--gen0-from`) | 새로 씀 |
| 판단 지점 | 고정 규칙만 | 1단계는 고정 규칙, 2단계에서 LLM 판단 허용 |
| 해결 못 한 오류 | 멈추고 기록 → 고친 뒤 `resume` | 다른 모델로 대체하고 기록 |
| 재개 시 모델 ID 변경 | 멈춤 | 경고 후 계속 |
| 채점 기준 자동 조정 | 끔 | 끔 (채점 기준 진화는 2번 논문의 주제) |
| 웹 검색 | 없음 | 없음 (나중에 옵션) |

실험 모드는 시작할 때 다음을 검사하고, 하나라도 어긋나면 시작하지 않아요.
- 모든 정책이 고정 규칙이에요.
- 세대 수가 정해져 있고, 조기 종료와 복구가 꺼져 있어요.
- 조건 값이 명단과 맞아요 (`same_family`의 짝 등).
- 모델 ID가 구성 파일에 고정돼 있어요.

## 7. 실행 후 작업 (`diagnose`)

엔진과 분리된 작업이에요. 저장된 텍스트로만 돌고, 결과는 `diagnostics/`에 적어요. 과제의 `data_sensitivity`에 맞는 점검기를 써요.

### 7.1 J2 진단 (기록만, 논문 분석 변수)

| # | 형식 | 질문 | 단위 |
|---|---|---|---|
| ① | Score 0~4 | 사실과 무관한 수사(강조, 과장, 반복)가 얼마나 많나 | 답마다 |
| ② | Noul | 답이 질문의 질환에 대한 그 정답지 항목의 임상시험 결과를 말하나 | 정답지 항목마다 (`--gold-items`) |
| ③ | Choice | 비판이 지적한 가장 큰 문제의 심각도: 없음, 사소함, 중대함, 치명적 | 심사 출력마다 |

- ②는 모든 모델의 학습 컷오프 이후에 결과가 나온 항목에만 물어요. 그래서 "예"가 나오면 곧바로 오염 경보예요. 정답지 항목 파일은 `{"items": [{"item": "...", "outcome_date": "YYYY-MM-DD"}]}` 형식이에요.
- ③은 분석에서 그 심사위원의 점수와 비교해요. "비판은 중대한데 점수는 높음"이 자기선호의 직접 신호예요.
- 뺀 진단(변이의 비판 반영, 비판 쏠림, 다양성 등)은 필요하면 나중에 같은 기록으로 추가해요.

### 7.2 PMID 확인
- 모든 답의 PMID를 모아서, 같은 번호는 한 번만 PubMed E-utilities로 조회해요. 제목, 초록, MeSH, 물질명을 가져와요.
- 번호가 존재하는지만 보면 부족해요. 무작위 번호 50개 중 47개가 실제 논문이었어요. 그래서 제목, 초록, MeSH, 물질명에 그 항목 이름이 나오는지로 판정해요. 항목이 `A–B` 같은 쌍(예: 리간드–수용체)이면 A와 B가 모두 나와야 해요.
- 결과는 답과 항목과 번호마다 셋 중 하나예요: **맞는 논문**, **엉뚱한 논문**, **없는 번호**. 빈 칸 수도 함께 세요.
- 계보를 보고 번호가 부모에게서 물려받은 것인지, 이번 세대에 새로 생긴 것인지 표시해요.

## 8. 명령과 구성 파일

```
reasonlineage run TASK.json --config configs/main.json \
    --mode experiment --judges recuse --context isolated --generations 3 \
    [--seed 42] [--gen0-from RUN_DIR] [--replay RUN_DIR] [--out runs/]
reasonlineage resume RUN_DIR
reasonlineage diagnose RUN_DIR [--gold-items GOLD.json]
```

구성 파일 `configs/main.json`:
```json
{
  "panel": [
    {"name": "opus", "backend": "claude", "model": "claude-opus-5-5", "effort": "xhigh"},
    {"name": "gpt", "backend": "codex", "model": "gpt-6.1-sol", "effort": "xhigh"},
    {"name": "grok", "backend": "grok", "model": "grok-4.7", "effort": "xhigh"},
    {"name": "glm", "backend": "http", "model": "glm-5.3", "effort": "xhigh",
     "base_url": "https://ollama.com/v1", "family": "zai", "api_key_file": "~/.config/reasonlineage/ollama.env"}
  ],
  "checkers": {
    "jev": {"version": "jev-1.13.0", "api_key_env": "JEV_API_KEY", "api_key_file": "~/.config/reasonlineage/jev.env"},
    "deepseek": {"backend": "http", "model": "deepseek-ai/DeepSeek-V4-Flash-0731", "effort": "max",
                 "base_url": "http://esplhpc-cp088:6018/v1", "family": "deepseek"}
  },
  "checker_for": {"public": "jev", "private": "deepseek"},
  "concurrency_per_backend": 2
}
```
- `http` 백엔드는 `family`를 꼭 적어요. claude, codex, grok의 회사는 코드에 이미 있어요.
- 키가 필요한 `http` 백엔드(Ollama cloud)는 `api_key_file`을 적어요. 파일에 키가 없으면 실행 전 점검에서 멈춰요.
- jev 키는 `api_key_env` 환경 변수가 있으면 그 값을, 없으면 `api_key_file`을 프로그램이 직접 읽어요. 키 파일은 저장소 밖에 두고, Claude Code 설정의 읽기 금지 규칙(`Read(~/.config/reasonlineage/**)`)으로 Claude의 도구가 열지 못하게 해요.
- 스크립트용 명단 문법(`name=backend:model[:effort]`)은 그대로 둬요.

## 9. 테스트

기본 실행(`pytest`)은 `live` 표시가 없는 테스트만 돌아요. 지금 있는 단위 테스트 72개는 그대로 둬요.

새로 추가할 테스트:
1. **가짜 패널로 끝까지 돌리기:** 정해진 답을 돌려주는 가짜 백엔드 4개로 3세대 실행을 몇 초 만에 돌려서, 흐름과 기록 전체를 확인해요.
2. **이어 돌리기:** 가짜 실행을 여러 지점에서 끊었다가 `resume`해도, 끊지 않은 실행과 결정(생존자, 결과)과 기록 내용이 같은지 봐요.
3. **replay:** `--replay`가 같은 결과를 내는지, 프롬프트 하나를 바꾸면 그 호출만 새로 부르는지 봐요. `--gen0-from`이 0세대만 재사용하는지도 봐요.
4. **점검기 격리:**
   - `core`와 `engine`이 `checks`를 불러오지 않는지 소스의 import를 검사해요.
   - 관문이 꺼져 있을 때 `checks.jsonl`을 지우거나 바꿔도 결과가 같은지 봐요.
   - `private` 과제에서 jev가 불리지 않는지 봐요.
5. **규칙 확인:**
   - `recuse`에서 작성자가 자기 답을 채점하지 않는지 봐요.
   - 교차를 맡은 모델이 부모 작성자가 아닌지 봐요. 대체 규칙이 쓰였으면 경고가 남는지도 봐요.
   - 생존자를 다시 채점하지 않는지, 조건마다 심사위원 구성이 맞는지 봐요.
6. **크기 규칙과 교차 담당:** N = 1~5에서 s, P, k가 맞는지, 교차 담당이 동률일 때 최근에 교차를 맡지 않은 모델 차례로 도는지 봐요.
7. **실험 모드 검사:** 규칙에 어긋난 설정이면 시작하지 않는지 봐요.
8. **seed:** 호출별 seed가 실행 seed와 호출 이름만으로 정해지는지, 재시도하면 달라지는지 봐요.
9. **답 형식과 PMID 판정:** 형식 B 검증(후보 누락·중복, 산문 불일치)을 봐요. PMID 판정은 가짜 PubMed 응답으로 확인해요.
10. **deepseek 확률 읽기:** 추론 토큰이 섞인 로그확률 목록에서 마지막 선택지 토큰을 읽는지 봐요.
11. **실제 호출 (`live`):** 백엔드마다 격리를 확인해요. GLM과 deepseek의 HTTP 호출(형식 B 출력, 로그확률)도 확인하고, jev는 크레딧을 산 뒤에 확인해요.
